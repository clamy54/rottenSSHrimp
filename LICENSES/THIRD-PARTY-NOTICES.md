controlled absolute paths, and must be present on the target system (or shipped
inside the `.app` bundle, in which case their licence texts ship with it).

The "Shipped in .app" column says whether `scripts/make-app.sh` copies the
library into `Contents/Frameworks/`. Everything it ships, it also
**distributes**, so the licence text below ships with it, in

The bundling is **recursive**: `make-app.sh` follows the Homebrew dependency
chain, so the `.app` also embeds *transitive* dylibs: typically OpenSSL
(`libcrypto`/`libssl`, Apache-2.0, OpenSSL-Apache-2.0.txt), zlib (zlib
licence, zlib.txt), libjpeg-turbo (BSD-3-Clause + IJG, libjpeg-turbo.txt) and
cJSON (MIT, cJSON-MIT.txt). Embedding is distributing: their licence texts
live in this directory and ship with every package. The per-release SBOM
(`sbom.cdx.json`, generated by `scripts/gen-sbom.sh`) lists what a given
bundle actually embedded, with full SHA-256 fingerprints.

Versions are those of the build machine at the time of writing; the release
manifest and SBOM pin the exact ones. On macOS,
SQLite is loaded from the operating system and never bundled, so nothing of
it is distributed there. On Windows, `sqlite3.dll` **is** shipped (public
domain: no notice text is required, provenance and hash are recorded in
`packaging/windows/DEPS.md`).

### libvncclient and the GPL-3 question

VNC sessions use `libvncclient`, from the LibVNCServer project. Its licence is
**GPL-2.0-or-later**: every source file carries the standard notice ending with
"either version 2 of the License, or (at your option) any later version".

That "or later" clause is what makes this project lawful. It permits the
library to be used under GPL-3, so combining it with RottenSSHrimp
(GPL-3.0-or-later) needs no relicensing and produces a coherent GPL-3 work.

**This must be re-checked on every version bump, not assumed once.** A
GPL-2.0-**only** component would be *incompatible* with GPL-3, and the
incompatibility would be entirely silent: it would compile, link and run
exactly the same, ship without complaint, and be discovered years later by
somebody reading the dependency list with a lawyer's enthusiasm. No compiler
warns you about a licence. Version pinning below is therefore a compliance
control, not merely a reproducibility one.

We build `libvncclient` **ourselves** from pinned, patched source rather than
using a system package; the transitive dependencies of *our* build are
libjpeg-turbo (BSD-style) and zlib (zlib licence), both GPL-3 compatible. We
deliberately build **without** TLS/SASL/crypto backends (GnuTLS, OpenSSL,
libgcrypt, Cyrus SASL), which removes those from the dependency set entirely
and shrinks the attack surface. VNC sessions use plain RFB authentication.

**Modifications made to libvncclient (GPL-3.0 section 5a).** The library is
modified: **three** security patches are applied to the pinned 0.9.15 source
before building. Two come verbatim from the LibVNCServer master branch (fixes
merged after the 0.9.15 release, no fixed release exists); the third is authored
locally (no public upstream fix at the time of writing):

- `0001-CVE-2026-44988-tight-gradient-overflow.patch`: `tight.c`, bounds the
  Tight *Gradient* filter to 2048 px (upstream commit `5b27054`);
- `0002-CVE-2026-50538-ultrazip-subrect-bounds.patch`: `ultra.c`, bounds
  UltraZip subrectangle parsing against the decompressed buffer (upstream commit
  `009008e`);
- `0003-tight-decode-rows-oob-write.patch`: `tight.c`, **locally authored**,
  bounds the number of decompressed Tight scanlines to the announced rectangle
  height before writing them into the framebuffer.

All three address pre-authentication heap out-of-bounds accesses reachable from
a malicious or MITM VNC server; the system 0.9.15 packages ship them unfixed.
The CVE identifiers in the patch names are best-effort and not independently
verified (see `third_party/libvnc/README.md`); trust the per-patch code
description above.

**Corresponding source (GPL-3.0 section 1).** The complete corresponding
source of the embedded `libvncclient` is, together in this repository:

- `third_party/libvnc/LibVNCServer-0.9.15.tar.gz`: the pinned upstream
  tarball itself, **archived in the repository** (so the source stays
  available if upstream moves, since a hash alone reconstructs nothing);
- `third_party/libvnc/SHA256SUMS`: its pinned hash;
- `third_party/libvnc/patches/`: the modifications above;
- `scripts/build-libvnc.sh`: the exact build recipe (verify, patch,
  configure flags, compile; it prefers the archived tarball and only
  downloads as a fallback);
- `scripts/gen-vnc-offsets.c`: regenerates the struct offsets the binding
  reads, against this exact build.

Any binary release **must** ship these, archived tarball included.
`scripts/make-linux-dist.sh` copies and re-verifies it into
`source/libvnc/`; the macOS DMG accompanies the published repository, which
now archives it. The dynamic binding `bindings/libvnc/uLibVncApi.pas` is our
own work under this project's licence.

The Monaspace fonts are redistributed unmodified, as required by this
project's policy. The reserved font names are not reused.

## Tree node icons

Two icon sets are embedded as binary resources. `icons/README.md` maps each
source directory to its upstream project; this section is the licence side of
the same story.

**Tabler Icons** (https://tabler.io/icons), MIT. The 126 monochrome sources in
`icons/folders`, `icons/hosts` and `icons/extended-set`, recoloured to
black-background and white-background variants and resized to 16/24/32/48 px.
The MIT license permits modification and redistribution; its notice is kept in
Tabler-MIT.txt.

**Papirus icon theme**
(https://github.com/PapirusDevelopmentTeam/papirus-icon-theme), **GPL-3.0**,
copyright Papirus Development Team, release `20250501` (see the version pin
below). Modifications made by this project, **in July 2026**: the icons were
selected (a subset of 36 out of the theme), recoloured into a dark-background
and a light-background variant, resized to 16/24/32/48 px, and renamed to the
catalogue identifiers used in `nodes.icon_id`. No artwork was redrawn.

Selecting a subset **is** one of the modifications, and it is a permitted one:
neither the GPL nor the MIT licence contains an all-or-nothing clause, and
nothing in either obliges a redistributor to ship a complete upstream package.
GPL-3.0 section 5 governs modified works, and a selection is a modified work.
What the licences require is stated below, and none of it is "ship everything".

Papirus is copyleft, unlike the permissive sets above. RottenSSHrimp is itself
distributed under GPL-3.0-or-later, so the combined work is compatible and no
relicensing is needed. Compliance obligations for redistributing binaries:

- the GPL-3.0 text is included (GPL-3.0-or-later.txt);
- the origin and license of the icons are stated here, in the README and in
  the application's About window;
- the modifications above are stated (GPL-3.0 section 5a);
- the corresponding source is available: the icon files this project builds
  from are kept in `icons/folders-dark`, `icons/folders-light`,
  `icons/hosts-dark` and `icons/hosts-light` in the project repository. These
  are **not** pristine upstream files. They are the recoloured variants
  described above, which is precisely why they must be shipped: they are the
  form in which this project modifies the artwork. The pristine upstream SVG
  sources are at the URL above, at the release named in the version pin.

Note from upstream, reproduced here: every application logo in the Papirus set
is owned by its respective trademark holder. Trademark rights are separate from
the copyright licence and are not granted by the GPL, a distinction people
discover in the order: use the logo, ship the logo, receive the letter.

## Corresponding Source: what a binary release MUST ship with

GPL-3.0 section 1 defines the Corresponding Source as "all the source code
needed to generate, install, and ... run the object code and to modify the
work, **including the scripts to control those activities**". Shipping a
`.app` or `.dmg` without these is a licence violation, even though the code
itself is public.

Beyond the Pascal sources, the following are part of the Corresponding Source
and must be distributed (or offered) with any binary release:

| Item | Why it is required |
|---|---|
| `scripts/gen-tree-icons.lpr` | Generates every embedded icon resource from the sources below. Without it the resources cannot be regenerated. |
| `scripts/gen-vnc-offsets.c` | Generates the verified `rfbClient` struct offsets used by the libvncclient binding. Without it those offsets cannot be re-derived for another libvncclient build, and the binding cannot be safely modified. |
| `scripts/build-libvnc.sh`, `third_party/libvnc/patches/`, `third_party/libvnc/SHA256SUMS` | Corresponding source of the **embedded, modified** `libvncclient`: the pinned tarball hash, our two security patches, and the exact build recipe. See "libvncclient and the GPL-3 question" above. |
| `icons/folders`, `icons/hosts`, `icons/extended-set` | Monochrome icon sources (Tabler) consumed by that script. 126 files, of which 85 are the extended set. |
| `icons/folders-dark`, `icons/folders-light`, `icons/hosts-dark`, `icons/hosts-light` | Colour icon sources (Papirus) consumed by that script. |
| `icons/README.md` | States the provenance and licence of each source directory. |
| `scripts/build.sh`, `scripts/make-app.sh`, `dist/` | Build and packaging scripts. |
| `app/rottensshrimp.lpi` | Declares the embedded resources; the build cannot be reproduced without it. |
| `resources/` | Embedded fonts and generated icon PNGs. |

In practice the published repository contains all of it, so pointing to the
repository satisfies the obligation. The trap is a *partial* source tarball.
Dropping `scripts/` or `icons/` to save a few megabytes looks like tidying,
reads like tidying in the commit message, and quietly turns a lawful
distribution into an unlawful one. Nothing fails. Nothing warns. The archive
just stops being the Corresponding Source.

### Papirus version pin

**Pinned reference: release `20250501`** (1 May 2025),
`https://github.com/PapirusDevelopmentTeam/papirus-icon-theme/tree/20250501`.

The icons were taken from the latest published Papirus release at the time
they were added to this project (July 2026), which is `20250501`. This is
confirmed by the project owner, who selected them.

All 36 icon names shipped in `icons/folders-dark`, `icons/folders-light`,
`icons/hosts-dark` and `icons/hosts-light` were independently verified present
as SVG sources in that release. Reproduce the check with:

```sh
curl -s "https://api.github.com/repos/PapirusDevelopmentTeam/papirus-icon-theme/git/trees/20250501?recursive=1" \
  | python3 -c "import json,sys,os; t=json.load(sys.stdin)['tree']; \
      print({os.path.basename(e['path'])[:-4] for e in t if e['path'].endswith('.svg')})"
```

Two points to keep straight:

- The pin rests on the owner's statement plus a name-level check, not on
  metadata in the files: the PNGs carry no upstream revision (they were
  rendered at 240x240 through Inkscape, per their `tEXtSoftware` chunk). This
  has one purpose: that the matching
  upstream SVG sources can be retrieved, and from `20250501` they can.
  **Anyone adding icons later must re-record the release they came from**, or
  this pin silently becomes wrong for part of the set.
- The `-dark`/`-light` pairs are **this project's own work**, not the upstream
  `Papirus` / `Papirus-Dark` split. Only 7 of the 36 names exist in both
  upstream themes; the remaining 29 exist solely in `Papirus`. The two
  variants shipped here were produced by recolouring, and that modification is
  already declared above under GPL-3.0 section 5a.

The authoritative build input remains the PNG set committed to this
repository: it is what `scripts/gen-tree-icons.lpr` consumes, and it is the
form in which this project actually works on the icons. That set, plus this
pin, is what a redistributor needs.
